# Database

PostgreSQL 16, accessed exclusively through Prisma 5.22 (`prisma/schema.prisma`, client singleton at `lib/prisma.ts`). Only files under `repositories/` may import the Prisma client — see [architecture.md](architecture.md).

## General Principles

* Verify the schema before making assumptions — read `prisma/schema.prisma`, don't infer table shape from a UI mockup or an old memory of the project.
* Preserve existing production data. This is a financial/inventory system (purchase orders, stock levels, costs) — never write a change that silently drops or truncates data.
* Prefer additive changes over destructive changes: add a nullable column or a new table before renaming/dropping an existing one; deprecate in two steps (add new, migrate data, remove old) rather than one.
* IDs are `cuid()` strings everywhere (no auto-increment integers) — follow this for any new model.
* Money and quantity fields use Prisma `Decimal` (e.g. `unitCost`, `quantity`, `standardCost`), never `Float` — floating point is unacceptable for currency/inventory math. Do arithmetic with Decimal methods (`.add`, `.sub`, `.mul`, `.greaterThan`), not `Number(...)`.
* Date-only values (a delivery date, a needed-by date) are stored as UTC midnight (`new Date('YYYY-MM-DD')`) and displayed with `.slice(0, 10)`. "Today" for business rules is computed in Asia/Manila (`lib/dates.ts`).

Workflow for a schema change:

1. Edit `schema.prisma`.
2. Generate the SQL: `npx prisma migrate diff --from-schema-datasource prisma/schema.prisma --to-schema-datamodel prisma/schema.prisma --script` into a new `prisma/migrations/<timestamp>_<name>/migration.sql` (or `prisma migrate dev --create-only` when the SQL needs hand edits).
3. **Read the SQL** before applying it.
4. `npx prisma migrate deploy`, then `npx prisma generate`.
5. Restart `npm run dev` **and** `npm run worker` — both hold the old generated client.

Things Prisma's schema language cannot express — standalone sequences, partial indexes, CHECK constraints — are hand-appended to the migration SQL with a comment. `migrate diff` ignores sequences and CHECK constraints, so they cause no drift. CHECKs in use: `BOM_kind_source_check` (a `CONVERSION` BOM has a source and a quantity > 0, a `PRODUCTION` BOM has neither) and `FinishedGoodLot_one_source_check` (a lot comes from exactly one production order or conversion order).

## Relationships

The schema (29 models) groups into these domain areas — see [architecture.md](architecture.md#data-model) for the narrative version:

* **Identity**: `User.branchId → Branch` (optional — a user isn't necessarily tied to one branch, e.g. `ADMIN`/`PROCUREMENT_MANAGER`; only `/api/auth/register` sets it, and nothing reads it for permissions).
* **Branches** (Week 8 Task 1): `Branch.name` and `code` are unique (`code` 2–10 upper-case letters/digits, fixed once created; the service also refuses a name differing only in case). `type` (`BranchType`): `COMMISSARY` supplies other branches, `OUTLET` receives from one — every branch cooks, so nothing else depends on it yet. `managerId` → `User` (relation `BranchManager`), `@unique`: one manager per branch and one branch per manager, enforced by the database; the service only accepts a `BRANCH_MANAGER` user, and assigning one who runs another branch clears that branch's `managerId` in the same transaction. **Who acts for a branch is read from `Branch.managerId`**, not from `User.branchId` or the login token's `branchId` (up to 8 h stale). `isActive = false` is a soft delete — branches are never deleted — refused while the branch has a non-zero `InventoryLevel` or `FinishedGoodLevel` (negative included) or open documents (production orders not `COMPLETED`/`REJECTED`/`CANCELLED`, `DRAFT`/`PENDING_APPROVAL` receiving reports, pending conversions or write-offs), and for the last active commissary: changing an active commissary to an outlet or deactivating it locks every active commissary row (`SELECT … FOR UPDATE`) first.
* **Item master**: `Material` and `FinishedGood` both reference `Category` and `Unit`. `FinishedGood.shelfLifeHours` (whole hours, 1–720, nullable) is how long it keeps once cooked; a production completion cannot be approved while it is null (Week 6 Task 4). `Category.type` is a free-text field (`'RAW_MATERIAL' | 'FINISHED_GOOD' | 'PACKAGING'`, listed as `CATEGORY_TYPES` in `category.repository.ts`) rather than an enum. `ItemPrice` holds dated reference prices per material, optionally per supplier; the effective price is the newest row on or before the date asked.
* **BOM**: `FinishedGood → BOM (1:N, versioned via BOM.version + isActive, unique per finished good + kind + version) → BOMItem (1:N) → Material`. Quantities are per batch of `batchSize`. Old versions are kept (`isActive = false`), never deleted — supersede, don't hard-delete. `BOM.kind` (Week 7 Task 1): `PRODUCTION` (made from materials by a production order) or `CONVERSION` (made from another finished good — `sourceFinishedGoodId`, `sourceQuantity` per batch in that good's unit — plus the `BOMItem` materials, by a conversion order). A finished good has at most one active version **per kind**, and each kind numbers its own versions (Lechon Paksiw: v1 and Conversion v1). Production planning reads `PRODUCTION` only (`findActiveByFinishedGood` takes the kind).
* **Procurement chain**: `PurchaseRequest (1:N) → PurchaseOrder (purchaseRequestId nullable) (1:N) → ReceivingReport`. Each stage has its own line table and status enum; transitions are enforced in the service layer, not by the database.
  * `PRStatus`: `DRAFT → PENDING_APPROVAL → CONVERTED_TO_PO | REJECTED`. Approval generates the draft order in the same transaction, so a request goes straight to `CONVERTED_TO_PO`; `APPROVED` exists in the enum but is never left standing.
  * `POStatus`: `DRAFT → PENDING_APPROVAL → APPROVED | REJECTED`, then `SENT → PARTIALLY_RECEIVED → FULLY_RECEIVED`, set by RR approval from the cumulative accepted quantity per line (all lines full → fully; some → partially; none, e.g. an all-rejected delivery → stays `SENT`); `CANCELLED` exists but is not yet used. `supplierId` is null on a freshly generated draft; `submittedById` records who submitted it.
  * `RRStatus`: `DRAFT → PENDING_APPROVAL → APPROVED | REJECTED`. `ReceivingReport.branchId` is where the delivery arrived; `receivedById` is who counted it (whoever last saved it). Each `ReceivingReportItem` links to its `PurchaseOrderItem`; `orderedQuantity` and `unitCost` are copied from the PO line. `expectedQuantity` is what was outstanding on the PO line when the line was saved — variance (short / over-delivered / rejected) is measured against it and derived, never stored. Stock in = `receivedQuantity − rejectedQuantity`. Outstanding per PO line = ordered − accepted across **approved** RRs only.
  * `REJECTED` is terminal for all three.
* **Inventory**: `InventoryLevel` is current-state (one row per `materialId` + `branchId`, `@@unique`). `StockMovement` is an append-only ledger, also per material + branch. Every row names its source document via `referenceType`/`referenceId` — both `NOT NULL`, but polymorphic, so not a real FK: the database guarantees a reference exists, not that it points at a valid row. **`quantity` is signed** — positive into stock, negative out of it — so a balance is `SUM(quantity)`, and for each (material, branch) the ledger's sum must equal `InventoryLevel.quantity` (the Stock Ledger page checks this). Direction cannot come from `MovementType` alone: a `TRANSFER` is out at one branch and in at another. Any code that writes inventory must update `InventoryLevel.quantity` and insert a `StockMovement` row **in the same transaction**, never one without the other — use `InventoryRepository.stockIn(tx, …)`, which does both on the caller's transaction, rather than writing either table directly. The level change is an upsert on the unique key with `increment`, which Prisma issues as one `INSERT … ON CONFLICT DO UPDATE` (atomic, no lost updates). `StockMovement.unitCost` is the purchase cost per unit on a receiving `IN`, and on a production `OUT` the reference price the run was costed at (Week 6 Task 3); null where no cost rule exists yet (adjustments, transfers). `InventoryLevel.updatedAt` is therefore the time of the last movement for that material at that branch, and the stock map reads it as such instead of scanning the ledger — so never update a level row except together with a movement. Writers: RR approval (one `IN` per line with accepted > 0, `referenceType 'ReceivingReport'`, `referenceId` = the RR), production completion approval (one `OUT` per ingredient through `InventoryRepository.stockOut`, `referenceType 'ProductionOrder'`) and conversion approval (one `OUT` per added ingredient, `referenceType 'ConversionOrder'`, `unitCost` = the reference price on the conversion date). Write-offs move finished goods only, never `StockMovement`. A level may go below zero: an approved completion records what physically left the shelf even when the books never received it (Week 6 Task 2, D3).
* **Finished goods stock**: kept per **lot** — one production run's output — because cooked food is perishable and expiry, transfers and write-offs all act on a lot. `FinishedGoodLot` (`lotNumber` unique; a lot takes the number of the document that made it — `PRD-…` or `CNV-…`; `productionOrderId` and `conversionOrderId` both unique and nullable, exactly one set (CHECK `FinishedGoodLot_one_source_check`) — at most one lot per run or conversion; `producedOn` = the Manila date the kitchen reported the run done, or the conversion was recorded; `expiresAt` = the moment it was reported done + the finished good's `shelfLifeHours`, fixed when the lot is created so a later shelf-life change never moves a labelled lot — null only for lots made before expiry was tracked; a lot's 24 / 48 h flag is derived from it on read — `expiryFlag` in `lib/dates.ts` — never stored), `FinishedGoodLevel` (current quantity per lot + branch, `@@unique`) and `FinishedGoodMovement` (append-only ledger per lot + branch, **signed** quantity, `referenceType`/`referenceId` NOT NULL). The same invariant as materials: the ledger's `SUM(quantity)` per lot and branch equals the level, and both change together through `FinishedGoodStockRepository` (`receiveLot` in; `takeFromLot` out — a lot never goes below zero, the decrease only applies while the level covers it) on the caller's transaction. `takeFromLot` writes an `OUT` row, or a `WASTE` row when told to (a write-off). A writer taking from lots locks them first (`lockLots`: `SELECT … FOR UPDATE` on the good's level rows at the branch, in id order) and plans with `planFefoTakes` (soonest expiry first, expired skipped). Separate from `InventoryLevel`/`StockMovement` rather than generalised: a nullable material-or-finished-good reference would need partial unique indexes that Prisma's upsert cannot use. The daily `stock-reconciliation` job checks both ledgers. A lot's `IN` row carries `unitCost` = its run's (or conversion's) cost per unit — what a lot is valued at on the Finished Goods page, what a conversion takes it at, and what Week 7 write-offs will cost it at. A conversion's source `OUT` rows carry the lot's own cost. The End of Day page (Week 7 Task 4) reads this ledger alone: per good and branch, `SUM(quantity)` before the day (opening), within it by flow, and before its end (closing), each movement valued at its lot's first `IN` `unitCost`; a movement is classified by `type` + `referenceType` (`DAY_FLOWS` in the repository — `IN`·`ProductionOrder` produced, `IN`/`OUT`·`ConversionOrder` converted in / out, `WASTE`·`WriteOff` written off, `TRANSFER` distributed). Nothing is stored.
* **Production**: `ProductionOrder` pins `finishedGoodId` + `bomId` + `branchId` + `requestedById` together, so a production run always records exactly which BOM version was used.
  * `ProductionStatus`: `DRAFT → PENDING_APPROVAL → APPROVED | REJECTED → IN_PROGRESS → PENDING_COMPLETION → COMPLETED`, plus `CANCELLED`. Built so far: create / edit drafts (Week 5 Task 1), submit `DRAFT → PENDING_APPROVAL` and the decision `→ APPROVED | REJECTED` (Task 5), start `APPROVED → IN_PROGRESS` and cancel `DRAFT | PENDING_APPROVAL | APPROVED → CANCELLED` (Task 6), and the kitchen's completion report `IN_PROGRESS → PENDING_COMPLETION` (Week 6 Task 1). Accounting's sign-off (Week 6 Task 2): approve `PENDING_COMPLETION → COMPLETED`, which in the same transaction deducts every ingredient of the pinned BOM at the **planned** quantity (one `OUT` per material, written in `materialId` order so two approvals cannot deadlock) and adds the **actual** yield as a new lot; or send it back `→ IN_PROGRESS` with a reason. The decision's `UPDATE` also matches the `completedAt` the approver was shown, so a report that was sent back and re-made meanwhile is never approved at the old figure. `REJECTED` and `CANCELLED` are terminal; an in-progress or completion-pending run cannot be cancelled (its ingredients are being used — a write-off, Week 7). `submittedById` records who submitted (null until then); whoever submitted cannot decide it.
  * Costing (Week 6 Task 3): recorded when accounting approves the completion, in the same `UPDATE` as the status, and never recomputed — `ItemPrice` can be back-dated, and a signed-off cost must not move. `plannedCost` = the pinned BOM at the planned quantities × the reference price (`ItemPrice`, `supplierId` null) in force on `plannedDate`; `actualCost` = the same quantities at prices on the lot's production date (the batch cost); `costPerUnit` = `actualCost ÷ actualQty`; `costVariance` = `actualCost − plannedCost ÷ plannedQty × actualQty` (positive = over plan: price changes and yield loss together). Pesos, unrounded (shown to the centavo). A missing price on either date blocks approval. Null on every other status; an open order's cost is an estimate derived on read.
  * Completion: `actualQty` is the yield the kitchen reported (> 0 and ≤ 2 × `plannedQty`, in the same unit), `completedAt` when it reported it, `completedById` who — all set by the same `UPDATE` as the status. `completedById` is for the rule that nobody approves their own completion; when accounting signed it off is on the status log. No stock moves until then. A send-back clears all three; each report's yield stays on the log as its note ("Yield 9.6 kg").
  * `batchWeight` (output of one batch, in the BOM's batch unit — the service refuses a BOM whose batch unit differs from the finished good's unit) × `batchCount` (whole number, 1–100) = `plannedQty`, computed in Decimal and stored because Week 6 compares `actualQty` with it. `plannedDate` is a date-only value (UTC midnight).
  * `bomId` is the finished good's **active** version, re-pinned on every save of a draft; the pin becomes permanent at submission. `requestedById` is the creator and does not change when someone else edits the draft.
  * Material requirements are **not stored**: they are the pinned BOM's lines scaled to `batchWeight` (per batch) and `plannedQty` (total), recomputed on read. The pinned version never changes, so a stored copy could only drift from it. What a run actually consumed is a separate record (Week 6).
  * The stock check is derived too: `InventoryLevel` at the order's branch, minus the requirements of other `APPROVED` / `IN_PROGRESS` / `PENDING_COMPLETION` orders there (`COMMITTING_STATUSES` in `production-order.repository.ts`) — stock only leaves when a completion is approved, so those are still on the books but spoken for. Nothing is reserved in the database. A line's shortage is `max(required − max(available, 0), 0)`: never more than the run's own requirement, so when other orders have over-committed the stock, each order reports only its own need (fixed 2026-11-08; before, two approved runs each counted the other's demand).
* **Distribution**: `StockTransfer` has two named relations to `Branch` (`TransferFrom`/`TransferTo`) — when querying, be explicit about which side you mean.
* **Conversions** (Week 7 Task 1): `ConversionOrder` records a conversion already done in the kitchen (unsold Lechon → Lechon Paksiw) — `orderNumber` (`CNV-000001`), the pinned `CONVERSION` `bomId`, `finishedGoodId` (output) and `sourceFinishedGoodId` (named relations `ConversionOrderOutput` / `ConversionOrderSource`), `branchId`, `submittedById` (who recorded it — never its approver), `sourceQty` / `outputQty` (each in its good's unit), `notes`, `createdAt` (the moment it was recorded and submitted: its conversion date in Manila and the start of the output's shelf life).
  * `ConversionStatus`: created `PENDING_APPROVAL` (there is no draft) `→ APPROVED | REJECTED`; `REJECTED` is terminal — production records it again. The decision's `UPDATE` has `PENDING_APPROVAL` in its `WHERE`.
  * The added ingredients are **not stored**: the pinned BOM's lines × `sourceQty` ÷ `BOM.sourceQuantity` (multiplied first, so 1.5 × 25 ÷ 6 is exactly 6.25), recomputed on read and at approval.
  * Approval (one transaction): lock the source lots, re-plan soonest expiry first with expired lots skipped (short → nothing written), source `OUT`s per lot, added-ingredient `OUT`s in `materialId` order (may go negative), the output lot `IN` (`lotNumber` = the order number, `expiresAt` = `createdAt` + the output's shelf life), then the costs.
  * Costs, recorded at approval and never recomputed (pesos, unrounded; null until then): `sourceCost` = Σ kg taken × each lot's recorded cost per unit; `conversionCost` = the added ingredients × the reference `ItemPrice` in force on the conversion date; `costPerUnit` = (`sourceCost` + `conversionCost`) ÷ `outputQty` — also the output lot's `IN` `unitCost`. A missing price or shelf life refuses approval.
  * Submitting needs `sourceQty` ≤ the unexpired source on hand at the branch less what other `PENDING_APPROVAL` conversions there claim (derived, nothing reserved); output > 0 and ≤ 2 × what the recipe expects.
* **Write-offs** (Week 7 Task 2): `WriteOff` takes finished goods that cannot be used or converted out of stock at what they cost — one **lot** at one branch per write-off: `writeOffNumber` (`WO-000001`), `lotId`, `branchId`, `submittedById` (who recorded it — never its approver), `quantity` (in the lot's unit; part of a lot allowed), `reason` (`WriteOffReason`: `EXPIRED`, `SPOILED`, `DAMAGED`, `FAILED_QUALITY`, `OTHER` — categories for the Week 10 / 11 waste analysis; `notes` required for `OTHER`), `createdAt` (recorded and submitted).
  * `WriteOffStatus`: created `PENDING_APPROVAL` (no draft) `→ APPROVED | REJECTED`; `REJECTED` is terminal. The decision's `UPDATE` has `PENDING_APPROVAL` in its `WHERE`.
  * Submitting needs `quantity` ≤ the lot's level at the branch less other `PENDING_APPROVAL` write-offs of that lot (derived, nothing reserved). A conversion's available source also subtracts pending write-offs of unexpired lots.
  * Approval (one transaction): lock the good's lot levels at the branch (`lockLots`, the same lock a conversion takes), recheck the lot still holds `quantity` (else nothing is written), one `WASTE` `FinishedGoodMovement` (`referenceType 'WriteOff'`, `unitCost` = the lot's recorded cost per unit), then `unitCost` and `totalCost` (= `quantity × unitCost`, the peso value lost) on the write-off — recorded once, never recomputed; null until then.
  * Raw materials are not written off here (that waits for stock adjustments).
* **Production status log**: `ProductionStatusChange` — one row per status change of a `ProductionOrder` (`fromStatus`, `toStatus`, `changedById → User`, `note` = approval remarks or cancel reason, `createdAt`), append-only, written by `transition()` in `production-order.repository.ts` **in the same transaction** as the status update and only when the update matched a row, so the log cannot disagree with the status. Creation is not logged (the order row has `createdAt` / `requestedById`); edits are not logged. It drives the order page's timeline. Approval decisions are logged here *and* in `Approval` (which the other workflows use).
* **Approvals**: `Approval` is polymorphic — `referenceType` (`'PurchaseRequest' | 'PurchaseOrder' | 'ReceivingReport' | 'ProductionOrder' | 'ProductionCompletion' | 'ConversionOrder' | 'WriteOff'` — the last is accounting's decision on a production order's completion report, `referenceId` = the order, kept apart from the decision on its plan) + `referenceId`, one row per decision, with the approver, `decision`, `remarks`, `decidedAt`. The document's own status column says where it is now; `Approval` says who decided and why.
* **Notifications**: `Notification.userId → User`, with an optional polymorphic reference to the document; unread while `readAt` is null. `type` says what happened: `PR_SUBMITTED` (reference = the purchase request); `PRODUCTION_ORDER_SUBMITTED`, `PRODUCTION_ORDER_APPROVED`, `PRODUCTION_ORDER_REJECTED`, `PRODUCTION_COMPLETION_REPORTED`, `PRODUCTION_COMPLETION_APPROVED`, `PRODUCTION_COMPLETION_REJECTED` (reference = the production order); `PRODUCTION_SHORTFALL` (`referenceType` `ProductionOrderShortfall`, `referenceId` = the order — its link is the pre-filled purchase request); `CONVERSION_ORDER_SUBMITTED`, `CONVERSION_ORDER_APPROVED`, `CONVERSION_ORDER_REJECTED` (reference = the conversion order); `WRITE_OFF_SUBMITTED`, `WRITE_OFF_APPROVED`, `WRITE_OFF_REJECTED` (reference = the write-off); `LOW_STOCK`, `STOCK_MISMATCH`, `EXPIRY_ALERT` (Week 7 Task 3) and `END_OF_DAY` (Week 7 Task 4) from the daily jobs. The daily ones reference no document: `referenceType` is `LowStockCheck` / `StockReconciliation` / `ExpiryCheck` / `EndOfDaySummary` and `referenceId` the Manila date (YYYY-MM-DD), which is also what stops a second notification the same day. `readAt` is set by `POST /api/notifications/read` (only the user's own, only while null); the bell counts `readAt IS NULL` through `@@index([userId, readAt])`.

## Document numbers

`prNumber`, `poNumber`, `rrNumber`, `ProductionOrder.orderNumber` (`PRD-000001`), `ConversionOrder.orderNumber` (`CNV-000001`) and `WriteOff.writeOffNumber` (`WO-000001`) come from Postgres sequences — `pr_number_seq`, `po_number_seq`, `rr_number_seq`, `prd_number_seq`, `cnv_number_seq`, `wo_number_seq` — read with ``tx.$queryRaw`SELECT nextval('…')` `` inside the creating transaction and formatted `XX-000001` in the app. Sequences are gap-tolerant (a rolled-back transaction burns a number); uniqueness matters, contiguity does not. Never use `count() + 1`.

## Indexing

Postgres does not auto-index foreign keys, so every join or filter column needs an explicit `@@index`. Current indexes beyond the `@unique` keys:

* `Material(categoryId)`; `ItemPrice(materialId, effectiveDate)` and `(materialId, supplierId, effectiveDate)`
* `BOM(finishedGoodId, kind, isActive)`, `@@unique(finishedGoodId, kind, version)`; `BOMItem(bomId)`
* `PurchaseRequest(status)`, `(requestedById)`; `PurchaseRequestItem(purchaseRequestId)`
* `PurchaseOrder(status)`, `(supplierId)`, `(purchaseRequestId)`; `PurchaseOrderItem(purchaseOrderId)`
* `ReceivingReport(purchaseOrderId)`, `(status)`, `(branchId)`; `ReceivingReportItem(receivingReportId)`, `(purchaseOrderItemId)`
* `InventoryLevel @@unique(materialId, branchId)`
* `StockMovement(materialId, branchId, createdAt)` for per-item ledger history, `(referenceType, referenceId)` for a document's movements
* `ProductionOrder(status)`, `(branchId)`, `(plannedDate)`; `ProductionStatusChange(productionOrderId, createdAt)`
* `FinishedGoodLot` `@unique(lotNumber)`, `@unique(productionOrderId)`, `@unique(conversionOrderId)`, `(finishedGoodId)`, `(expiresAt)` (soonest-first listing; the daily `expiry-check`'s "expires within 48 h" query); `FinishedGoodLevel @@unique(lotId, branchId)`, `(branchId)`; `FinishedGoodMovement(lotId, branchId, createdAt)`, `(referenceType, referenceId)` — the End of Day queries filter on `createdAt` alone and scan the ledger; fine at a few thousand movements, add `(createdAt)` when it grows
* `ConversionOrder(status)` (inbox, pending source claims), `(branchId)`
* `WriteOff(status)` (inbox), `(lotId, status)` (pending claims on a lot), `(branchId)`
* `Approval(referenceType, referenceId)`; `Notification(userId, readAt)`

Not yet indexed, add with the feature that queries them: `StockTransfer` from/to branch.

## Large Data

* Paginate any list over a table that grows unboundedly. Repository list methods take `skip`/`take` (default `take: 50`) and return rows plus a count from one `$transaction` (`MaterialRepository`, `PurchaseOrderRepository`, `ReceivingReportRepository`).
* Batch bulk writes — `createMany`, nested `create` on a parent, or one `$transaction` — instead of one query per row.
* Use background jobs (BullMQ, see [architecture.md](architecture.md#infrastructure)) for anything that scans many rows or calls an external service: low-stock checks, escalations, report generation.
* Aggregate in the database (`aggregate`/`groupBy`) rather than pulling rows into Node — e.g. accepted quantity per PO line is one `groupBy` over approved RR lines, and variance lines per report one `groupBy` per list page. To compare two columns of the same row in a filter, use a Prisma field reference (`prisma.receivingReportItem.fields.expectedQuantity`).

## Multi-Tenant

This is not a multi-tenant system in the SaaS sense (no per-customer data isolation) — it's a single organization with multiple **branches**. Branch is a data-partitioning dimension, not a security boundary enforced at the database level:

* `InventoryLevel`, `StockMovement`, `FinishedGoodLevel`, `FinishedGoodMovement`, `ReceivingReport`, `StockTransfer` (from/to), `ProductionOrder`, `ConversionOrder` and `WriteOff` are branch-scoped via `branchId`.
* There is no row-level security or Prisma middleware restricting queries by branch — data access is gated by `middleware.ts` role guards and service rules, not by filtering results to the user's own `branchId`.
* If branch-level isolation becomes a requirement (a branch manager sees only their branch's inventory), add that filter explicitly in the service/repository layer — a route guard alone does not stop a broad query.

## Migration Checklist

Before creating a migration:

* **Backward compatibility** — will existing running code (or a mid-deploy old instance) still work against the new schema? Prefer nullable-then-backfill-then-required over adding a `NOT NULL` column directly to a table with existing rows. (The Week 3 and Week 4 migrations added `NOT NULL` columns directly only because the tables were verified empty first.)
* **Existing data impact** — check row counts and current values for any column being altered/dropped; a `Decimal` or enum change can silently truncate or fail on real data (e.g. removing an enum value breaks rows that use it).
* **Rollback strategy** — Prisma migrations are forward-only; know how you'd write the down-migration or restore from backup before running an irreversible change against real data.
* **Performance impact** — adding an index or `NOT NULL` constraint to a large table (`StockMovement` once populated) can lock it during the migration; check whether it needs to run outside peak hours or use a concurrent index build.
