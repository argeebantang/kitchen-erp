# Architecture

## Overview

KitchenERP is a single Next.js 15 application (App Router) that serves both the UI and the API from one deployable unit, plus one background worker process for queued jobs. Server code is organized into three layers so that HTTP concerns, business rules, and data access stay separate:

```
Route Handler (app/api/**/route.ts)
        ↓ validates input (zod), maps result → HTTP
Service (services/*.service.ts)
        ↓ business rules, orchestration, DTOs
Repository (repositories/*.repository.ts)
        ↓ Prisma queries only
Prisma Client (lib/prisma.ts) → PostgreSQL
```

Server Components under `app/(protected)/` read directly rather than round-tripping through the API routes — through a **service** when the data needs rules or DTO conversion (e.g. `PurchaseOrderService.getById` on the order page), or straight from a repository for a plain lookup (the protected layout's `UserRepository.findById`, the supplier list on the order and master-data pages). API routes exist for what the browser calls: auth, and every mutation (create, edit, submit, approve, send). Client Components receive plain data only — see "Server → Client boundary" below.

## Request flow & auth

1. **`middleware.ts`** runs on every request (matcher excludes static assets). It is the single point where authentication is enforced:
   - Public paths (`/login`, `/api/auth/login`) pass through. `/api/auth/register` is not public — it lets the caller choose a role, so it is ADMIN-only.
   - All other paths require a valid `kitchen-token` JWT cookie (HS256, 8h expiry, signed with `JWT_SECRET`, verified via `jose`). Missing/invalid tokens redirect to `/login`.
   - `ROLE_GUARDS` maps path prefixes to allowed `Role`s. **Every** matching prefix is checked, so overlapping guards are AND-ed: `/procurement` sets the baseline and narrower prefixes (`/procurement/orders`, `/procurement/approvals`, `/procurement/receiving`, and the matching `/api/*` prefixes) restrict further. A guard may name `methods`, applying only to those: the item-master and BOM APIs are guarded for writes (`POST`/`PUT`/`PATCH`/`DELETE`) while reads stay open to every signed-in user. A mismatch redirects to `/unauthorized`. The sidebar (`lib/navigation.ts`) mirrors these but only hides links; middleware is what blocks the URL.
   - On success, middleware injects `x-user-id`, `x-user-role`, `x-user-email` onto the forwarded request. Route handlers trust these headers instead of re-verifying the JWT — which is only safe on paths middleware guards.
   - Middleware runs in the **Edge runtime**, so everything it imports must be Edge-safe: it imports `lib/jwt.ts` (`jose` only), never `lib/auth.ts` (bcrypt) or Prisma. `next dev` tolerates a violation; only `next build && next start` exposes it.
2. **Server Components** call `getSession()` (`lib/session.ts`), which re-verifies the cookie. The protected layout also re-fetches the user, which catches users deleted after the token was issued.
3. **Login/Register/Logout** go through `AuthService`, which hashes/verifies passwords with bcrypt (12 rounds, with a dummy-hash comparison to avoid user-enumeration timing) and issues/clears the `kitchen-token` cookie (httpOnly, `secure` in production, `sameSite=lax`).

## Authorization: path vs action

A path guard can say who may reach a URL, not what they may do there. Where one path serves several roles doing different things, the service checks the role for the action:

- Accounting must reach `/api/purchase-orders` to approve, but must not edit a draft — `PurchaseOrderService.updateDraft` refuses non-procurement roles.
- Accounting reads `/procurement/receiving` to approve reports, but `/procurement/receiving/new` has its own procurement-only guard, and the edit page (`[id]/edit`, which no prefix can match) redirects other roles itself. `/production/orders/[id]/edit` does the same for production, ready for accounting to read production orders (Week 5 Task 5).
- `/procurement/requests/new?productionOrder=<id>` pre-fills a purchase request with a production order's shortfall. The page reads the order only for ADMIN, PRODUCTION_MANAGER and PROCUREMENT_MANAGER (procurement reaches it from the "approved — short on …" notification); for anyone else the parameter is ignored and the form is empty.
- Accounting reads `/production/orders` to approve production orders (the decision goes through `/api/approvals`); `/production/bom` and `/production/orders/new` keep their own ADMIN + PRODUCTION_MANAGER guards, and the edit page and Submit card check the role themselves. Nothing is created until the requester saves.
- Conversions (Week 7 Task 1) follow the same split: `/production/conversions` is readable by ADMIN, PRODUCTION_MANAGER and ACCOUNTING; `/production/conversions/new` and `/api/conversion-orders` are ADMIN + PRODUCTION_MANAGER; accounting decides through `/api/approvals`. The conversion page links the recipe only for roles that can open `/production/bom`.
- Write-offs (Week 7 Task 2): `/inventory/write-offs` is readable by ADMIN, PRODUCTION_MANAGER and ACCOUNTING; `/inventory/write-offs/new` and `/api/write-offs` are ADMIN + PRODUCTION_MANAGER, and the Finished Goods page shows the Write off action to those roles only; accounting decides through `/api/approvals`.
- End of Day (Week 7 Task 4): `/inventory/end-of-day` is readable by every signed-in role, like Finished Goods; its documents link to the production order, conversion or write-off only for the roles that can open those pages (`SOURCE_PAGES` in `services/inventory.service.ts`, shared with the Stock Ledger).
- All approve/reject decisions go through **one** endpoint, `POST /api/approvals` (guarded to ADMIN + ACCOUNTING), which dispatches on `referenceType`. Every other transition has its own endpoint (`.../submit`, `.../send`).
- The **Approvals inbox** (Week 11 Task 1, `/procurement/approvals`, in the Overview nav group) is one queue of every pending document, oldest first. `ApprovalInboxService.list` calls each document's own pending list (`PurchaseRequestService.list`, `ProductionOrderService.listPending`, …) and maps the results onto one `ApprovalItemDto` — it computes no figure itself, so the badges (short, price missing, lot short, variance) are the services' own. `components/procurement/ApprovalInbox.tsx` decides each row in place through `POST /api/approvals`; the services' rules (self-approval, still pending, a reason to reject) are the ones that hold. The page refreshes every minute (`AutoRefresh`).
- **Nobody approves their own work, ADMIN included.** The approver is compared with the person responsible (PR: requester; PO: `submittedById`; RR: `receivedById`, who is whoever last saved the draft — submitting does not change it; production order: `submittedById`; production completion: `completedById`, who reported the run done; conversion order and write-off: `submittedById`, who recorded it).

## Layers in detail

- **Route handlers** (`app/api/**/route.ts`): parse/validate bodies with `zod`, read the injected identity headers (401 if absent), delegate to a service, and translate the result into an HTTP response. They never import Prisma.
- **Services** (`services/`): business rules and orchestration across repositories. They return a typed result union — `{ success: true, data } | { success: false, error, status }` — rather than throwing, and they convert Prisma rows into DTOs (Decimals as strings) for the UI.
- **Repositories** (`repositories/`): the only layer allowed to import `lib/prisma`. Each is scoped to one model/domain concept, defines its `select`/`include` shapes (e.g. `safeUserSelect` excludes `passwordHash`), and owns transactions (`prisma.$transaction`) when a write spans several tables.
- **`lib/`**: `prisma.ts` (client singleton reused across hot reloads), `config.ts` (fails fast on missing env vars), `jwt.ts` (Edge-safe JWT), `auth.ts` (Node-only, adds bcrypt), `session.ts`, `navigation.ts`, `queue.ts` (BullMQ producer, Node-only), `realtime.ts` (Redis pub/sub for live updates, Node-only), `claude.ts` (the Claude API client, AI feature settings and model prices, Node-only — Week 9), `decimal.ts` (Decimal ↔ string, server-only), `format.ts` (display formatting usable on both sides), `dates.ts` (business-day helpers in Asia/Manila, and month-calendar arithmetic on date labels for the production schedule — no date library).
- **`worker/`**: the BullMQ consumer (see Infrastructure).
- **`components/`**: shared UI. `inventory/` holds the stock map (`StockMap`, `StockTile`); `inventory/BranchHeadline` and `BranchTransfers` make up the Branch Inventory page; `ui/AutoRefresh` is a generic polling helper and `ui/LiveRefresh` its push-driven counterpart. `ai/` holds AI Settings' `RecentAiCalls` and `TestConnection` (Week 9). `costing/` holds the costing dashboard's pieces, including `WeeklyColumnChart` — charts are SVG drawn in Server Components, no chart library — and `chart-colors.ts`, one colour per costing figure. Reusable procurement pieces: `StatusBadge`, `DecisionHistory`, `ApprovalActions`, `PurchaseRequestActions`, `PurchaseOrderActions`; form primitives in `components/ui/form.tsx`.

This is a conventional layered/n-tier architecture rather than DDD or hexagonal — repositories wrap Prisma calls fairly directly, and business rules live in services as plain objects of async functions.

## Patterns in use

- **Race-safe status transitions.** The expected current status goes in the UPDATE's `WHERE` (`updateMany({ where: { id, status: DRAFT } })`), and a zero-row result means someone else moved it first → 409. No read-then-write gap. Production orders route every transition through one helper, `transition()` in `production-order.repository.ts`, which also writes the `ProductionStatusChange` log row on the same transaction — only when the update matched.
- **Row locks for cumulative checks.** When a write depends on a total other transactions also change — RR approval checks accepted ≤ ordered per PO line — lock the parent row first (`SELECT … FOR UPDATE` via `$queryRaw`, e.g. `PurchaseOrderRepository.lockForReceiving`), then read the total inside the same transaction. A second approval on the same order waits, then sees the first's committed rows. Take locks in one order (order before report) so two transactions cannot deadlock. To abort with a reason from inside `$transaction`, throw a small error class and map it to a result outside (`ReceivingConflict` in `receiving-report.repository.ts`).
- **Stock writes** go through `InventoryRepository.stockIn` / `stockOut(tx, …)` for materials and `FinishedGoodStockRepository.receiveLot` / `takeFromLot(tx, …)` for finished goods: ledger row and level change together, on the caller's transaction. Writes that touch several level rows in one transaction take them in a fixed order (production completion and conversion approval: materials by `materialId`) so two such transactions cannot deadlock. Taking finished goods out of lots (conversion approval) first locks every level row of that good at the branch with `FinishedGoodStockRepository.lockLots` (`SELECT … FOR UPDATE`, in id order), re-reads them and plans with `planFefoTakes` — soonest expiry first, expired skipped — the same pure function the preview uses; a lot never goes below zero. A write-off approval takes the same lock, in the same order, so a conversion and a write-off on the same good cannot deadlock; it writes a `WASTE` movement.
- **Running totals over paged history** use a SQL window function (`SUM(quantity) OVER (ORDER BY "createdAt", id)` in `InventoryRepository.runningBalances`) computed over the full history and only then filtered to the page's rows, so a balance on page 3 is right without loading pages 1–2.
- **Polymorphic references on screen** resolve to document numbers in one batch query per document type per page (`InventoryService.ledger`), and become links only for roles that can open that page (`SOURCE_PAGES`).
- **Real-time push** (the notification bell): a change is published on Redis pub/sub (`lib/realtime.ts` — from the worker or the app, whichever wrote it); each Next.js server process holds one subscriber and forwards the signal down Server-Sent Events streams (`GET /api/notifications/stream`) to the affected users' tabs, where the browser's `EventSource` (`hooks/useNotifications.ts`) reloads from the ordinary API. The event carries no data, so there is one read path. Every (re)connect reloads, which covers anything published while disconnected. Publishing never fails the write it reports. Needs a long-running Node server.
- **Live pages by push** (Branch Inventory, Week 8 Task 5): the same pub/sub and subscriber, channel `inventory:changed` carrying branch ids. The services call `signalInventoryChanged` after any commit that changes stock or what a branch page shows (fire-and-forget, never awaited); `GET /api/inventory/stream?branch=` forwards it; `components/ui/LiveRefresh.tsx` debounces about 1 s and calls `router.refresh()`, and also refreshes every 2 minutes (expiry badges age with no signal) and on returning to the tab. A new stock-moving path must signal its branches too. The subscriber lives on `globalThis` across hot reloads, so a new channel needs one `npm run dev` restart in development.
- **Live pages poll.** `components/ui/AutoRefresh.tsx` calls `router.refresh()` on an interval while the tab is visible (Stock Levels: 30 s). The Server Component re-renders and client state survives; a Client Component that shows one item (the stock map's popup) stores its id, not the object, so it picks up the fresh figures. Keep what a polled page reads bounded — the stock map reads `InventoryLevel` (with its `updatedAt` as "last movement"), never the ever-growing `StockMovement`.
- **Document numbers** come from Postgres sequences (`pr_number_seq`, `po_number_seq`, `rr_number_seq`, `prd_number_seq`, `cnv_number_seq`, `wo_number_seq`, `trf_number_seq`) via `nextval()` inside the creating transaction, formatted `PR-000001` etc. `count() + 1` is not used — it issues duplicates under concurrency.
- **Server → Client boundary.** Prisma `Decimal` is a class instance and cannot cross into a Client Component; services stringify it with `toDecimalString` (`lib/decimal.ts`). Client code formats strings with `lib/format.ts` and may import service *types* only (`import type`), never values.
- **Next.js 15**: `params` and `searchParams` are Promises and must be awaited. `notFound()` renders the nearest `not-found.tsx`.
- **AI calls** (Week 9 Task 1) go through one function, `AiService.complete()`: no key → "not set up"; the month's estimated spend (`AiCall`) against `AI_MONTHLY_BUDGET_USD` → refused as `OVER_BUDGET` without sending; then `client.beta.messages.create` with the shared `BASE_SYSTEM_PROMPT` + the feature's instructions, the feature's model / effort / max tokens from `AI_FEATURES` (`lib/claude.ts`), adaptive thinking and the server-side refusal fallback; `stop_reason` is read before content (`refusal`, `max_tokens` are failures); SDK errors become a message and a status (`describeApiError`); every attempt is recorded with tokens and an estimated USD cost per attempt (`estimateUsage`). Features never import the SDK client. Spend is capped twice: this soft budget, and the Anthropic Console workspace's spend limit, set higher, as the hard stop.
- **Supplier lead time** (Week 10 Task 3): `SupplierService.leadTimes()` — measured (median days from PO approval to first approved delivery, last 180 days, 3+ orders), else promised (`Supplier.leadTimeDays`), else 2 days, with its source. The Reorder Recommender plans with it. KitchenAI reports share one findings format (`services/ai-findings.ts`: schema, parser, keep findings naming real rows).
- **Reorder Recommender** (Week 10 Task 4): `ReorderService.forAlerts` turns the stock map's 🔴/🟡 alerts into an order quantity and deadline from inputs read once per page (30-day usage via `groupBy`, the schedule via `ProductionOrderService.scheduledUse`, open purchase lines, supplier per material, `SupplierService.leadTimes`, last month's supplier facts); `recommend()` is pure. An open line counts for the kitchen in its `deliverToId` (the order's, else its request's); lines with none are shown, not counted. The stock map — and so Branch Inventory and the low-stock summary — covers kitchens only. Its explanation is an ordinary insight (`REORDER_RECOMMENDATION`, queued on Explain); `AiInsightRepository.findMany` loads a page's insights with their facts in one query, to flag text written from figures that have since moved.
- **AI insights, one door** (Week 10 Task 2): `POST /api/ai/insights` and `AiInsightService` (a registry per `AiInsightType`: who may ask, how) serve Ask / Try again / Regenerate for every insight; `components/ai/AiInsightPanel` shows any insight's state with the AI badge and Regenerate. Regenerate keeps the earlier text until the new one is written (`AiInsightRepository.regenerate`). Weekly and monthly AI reports run from `AI_SCHEDULED_JOBS` on the `ai` queue (same `upsertJobScheduler` as `DAILY_JOBS`). Structured output: `AiService.complete({ format })` passes a JSON schema as `output_config.format`; Feature 3's findings come back schema-valid and are checked against the facts' row ids.
- **AI features run in jobs** (Week 9 Task 2): a request marks an `AiInsight` `PENDING` (race-safe: a second request while one is `PENDING` or `READY` queues nothing) and queues a job on the separate **`ai` queue** with `AI_JOB_OPTIONS` (3 attempts, exponential backoff from 30 s). The job's service method calls `AiService.complete()` and writes `READY` or `FAILED`; a recoverable failure (`retryable`: rate limit, overloaded, unreachable) returns `RETRY` and the handler throws so BullMQ retries, unless it is the last attempt. Pages poll with `AutoRefresh` only while an insight is `PENDING`. **Code calculates, Claude explains:** every figure is computed in Decimal by the service and passed to Claude as facts to quote — Feature 1: `CostVarianceService` (comparison against the previous run of the same good, split into price and usage / yield effects), queued after a completion approval commits.
- **The assistant's tool loop** (Week 9 Task 3): `AiService.complete()` and `converse()` share `round()` — one call with the budget check, the `AiCall` row and the error mapping. `converse()` offers tools (strict JSON Schema, `tool_choice` auto), runs the ones Claude asks for and sends their results back in one user message (`is_error` for a failed lookup, so Claude can correct it), up to `maxRounds` (5); every round is its own `AiCall`. The system prompt is the base prompt + the cached instructions + a per-request context (today's Manila date) after the cache breakpoint; automatic caching covers the growing conversation. Tools live in `services/assistant-tools.ts`: each has a zod check of Claude's input (model output is untrusted), its roles and `available()`, and calls a service or repository. **`get_production_costs`** returns Decimal figures from `CostingService` (code calculates, Claude explains). **`run_query`** runs Claude's SQL through `AiReaderRepository` — a second Prisma client on `AI_DATABASE_URL`, the Postgres role `kitchen_ai_reader` — inside `SET TRANSACTION READ ONLY` + `statement_timeout`, wrapped as one subquery with our own `LIMIT`. What it can read is the role's grants (migration `20261119100000_ai_reader_role`), not the prompt; they are not per branch, hence `ASSISTANT_ROLES`.
- **Demand Forecaster** (Week 10 Task 5): `DemandForecastService.forecast(kitchenId, date)` reads the kitchen's requests day by day (`DemandForecastRepository.requestedByDay`, one query over the history window), the holidays, the planning recipes, the kitchen's finished-goods lots, the runs planned for the day and 30-day yields, and works out per good: demand (requests after the cut-off, else max(requests so far, same-weekday average over 8 weeks without holidays)) − stock still good → ÷ yield (≤ 100 %) − planned → batches. The cut-off rule is the stock requests' own `isLate`. Production → Plan renders it; the explanation is an `AiInsight` (`DEMAND_FORECAST`) with the same live-figures check as Feature 4.
- **Dashboard** (Week 10 Task 7): `DashboardService.forViewer` reads the stock map once and builds the four stat cards and "KitchenAI at a glance" (one tile per feature, gated by the roles that can open what it links to; the waste and supplier tiles reuse the cards' own figures). No Claude call; a branch manager gets none of it (company-wide figures).
- **Decision Simulator** (Week 10 Task 6): `DecisionSimulatorService.simulate` measures a what-if run with the order's own helpers — `consumptionByMaterial` (what sign-off deducts) and `committedAtBranch` (the stock check's committed quantities, extracted from `stockFor`) — and `ItemPriceRepository.findPricesAsOf` at the end of the day, as `costRun` does. Read-only; `POST /api/production/simulate` returns it, and with `explain` calls `AiService.complete` synchronously (like the assistant) without storing the text.
- **A purchase's kitchen** (Week 10 Task 4): `PurchaseRequest.deliverToId` is required by `PurchaseRequestService.create` (an active central kitchen — checked in the service because the assistant's Confirm creates requests too), copied onto the purchase order inside the approval transaction (`createDraftFromRequest`), and is the receiving form's default (`ReceivingFormDto.defaultBranchId`). The receiving report's `branchId` stays the record of where stock arrived. The assistant's `draft_purchase_request` resolves the kitchen like `draft_production_order` (`matchKitchen(term, 'receive')`).
- **Write actions** (Week 9 Task 5): confirm-before-execute. The `draft` tools (`draft_purchase_request`, `draft_production_order`; `kind: 'draft'`, ADMIN / PRODUCTION_MANAGER) call `AssistantActionService`, which resolves names to records on the server (`searchActive` on materials / finished goods), checks the draft under the document service's own rules (`ProductionOrderService.check`, `previewRequirements`, reference prices) and stores it on the question's `AiQuery` (`proposeAction`, one per question). Tools get `AssistantToolContext` (viewer + `queryId`) for this. Nothing is created until `POST /api/ai/assistant/actions/[id]`: `claimAction` (one conditional `updateMany` — the asker, PROPOSED, unclaimed, within 24 h) makes a double click create one document; the document is created through `PurchaseRequestService.create` / `ProductionOrderService.create` as the user (DRAFT, normal approval flow); a failure `releaseAction`s the claim. Claude never sees the panel, so the card adds what became of a draft to the history it resends.
- **The query log** (Week 9 Task 4): `AssistantService.ask()` writes an `AiQuery` `PENDING` before calling Claude, passes its id down so every round's `AiCall` carries `aiQueryId`, logs each tool call as it runs, and finishes the row `ANSWERED` or `FAILED` once (`WHERE status = PENDING`). Logging failures are caught and only logged to the server — never the user's problem. The conversation id is issued by the server (`node:crypto` `randomUUID`) and round-tripped by the card, because the browser's `crypto.randomUUID()` needs a secure context. Admins read the log at `/admin/ai/questions` (`AiQueryService.list`; rounds and cost summed from `AiCall` in one `groupBy` per page).
- **Email is a copy, never the record** (Week 11 Task 2). `createAndPush` inserts the notifications (`createManyAndReturn`, one INSERT), pushes the bell, then queues one `notification-email` job per emailed notification on the **`email` queue** (job id `notification-email-<notificationId>`, so a re-run cannot queue it twice; BullMQ refuses `:` in custom ids). The worker's third `Worker` sends them one at a time, at most 2 a second (Resend's default limit), with `EMAIL_JOB_OPTIONS` (3 attempts, 30 s backoff). `EmailService.sendNotification` skips a user with no address (not logged), logs `SKIPPED` without `RESEND_API_KEY`, and otherwise calls `lib/email.ts` — plain `fetch` to `https://api.resend.com/emails`, no SDK — with the notification id as `Idempotency-Key`, so a retry after a lost reply cannot send twice. Busy / 429 / unreachable → `RETRY` (the handler throws) until the last attempt; anything else → `FAILED` with Resend's message. `renderEmail()` is the one template (inline styles, every value HTML-escaped). Emails go only to `User.notificationEmail`, never the login email.
- **Queue failures never fail the user's action.** A request is submitted even if Redis is down; the enqueue is wrapped in try/catch after the status change commits.

## Data model

Defined in `prisma/schema.prisma` (36 models, PostgreSQL). Domain areas:

- **Identity**: `User` (role via `Role`: `ADMIN`, `PROCUREMENT_MANAGER`, `PRODUCTION_MANAGER`, `BRANCH_MANAGER`, `ACCOUNTING`, `VIEWER`), `Branch`. Branch profiles (Week 8 Task 1) are managed in Master Data through `BranchService`: a fixed `code`, a `type` (`COMMISSARY` supplies, `OUTLET` receives; every branch cooks), and one manager (`Branch.managerId`, unique) — code that decides who may act for a branch reads it there, not from the token. Deactivation is soft and refused while the branch holds stock or open documents, because every inventory page and form lists active branches only (`BranchRepository.findAllActive`), and for the last active commissary.
- **Item master**: `Category`, `Unit`, `Material`, `FinishedGood`, and `ItemPrice` (dated reference prices per material, optionally per supplier).
- **BOM**: `BOM` (versioned per finished good **and kind**, stated per batch of `batchSize`) and `BOMItem` lines pointing at `Material`. A `PRODUCTION` recipe is cooked by a production order; a `CONVERSION` recipe (Week 7) makes its good from another finished good (`sourceFinishedGoodId`, `sourceQuantity` per batch) plus its `BOMItem` materials, through a conversion order. Production planning only ever sees `PRODUCTION` recipes.
- **Procurement**: `Supplier`; `PurchaseRequest`/`PurchaseRequestItem` → `PurchaseOrder`/`PurchaseOrderItem` → `ReceivingReport`/`ReceivingReportItem`. Each stage has its own status enum (`PRStatus`, `POStatus`, `RRStatus`). An RR line links to its PO line; an RR records the branch it was received at and who counted it.
- **Inventory**: `InventoryLevel` (current on-hand per material per branch) and `StockMovement` (append-only ledger, per material per branch, typed by `MovementType`, signed quantity, always referencing its source document). Finished goods have their own, per **lot** (one production run's output): `FinishedGoodLot`, `FinishedGoodLevel` (per lot per branch) and `FinishedGoodMovement` (the same ledger rules), read through `InventoryService.finishedGoodStock` (`/inventory/finished-goods`). A lot comes into stock when accounting approves a run's completion (Week 6), with its expiry fixed then: the moment the run was reported done + the finished good's shelf life. Finished Goods lists lots soonest to expire first, flagged Expired / within 24 h / within 48 h (`expiryFlag` in `lib/dates.ts`, worked out against one clock per page or job, never stored; Week 7 Task 3). Read through `InventoryService.ledger` (`/inventory/ledger`) and `InventoryService.stockMap` (`/inventory/stock`, coloured by `stockStatus()`).
- **Production**: `ProductionOrder` (`ProductionStatus`: `DRAFT → PENDING_APPROVAL → APPROVED | REJECTED → IN_PROGRESS → PENDING_COMPLETION → COMPLETED`, plus `CANCELLED`; the kitchen reports a run done with its actual yield, and accounting's sign-off is what moves stock and records the run's cost — Week 6). Costing prices the BOM at reference `ItemPrice`s on a date in one query (`costRun` in `production-order.service.ts`): live as an estimate on open orders, stored at approval and never recomputed once completed — planned from a finished good's active BOM, pinning that version; drafts are created and edited at `/production/orders` (Week 5). Its material requirements are derived, never stored: the pinned BOM scaled to the order by `scaleBomQuantities`, in one service function (`materialRequirements`) that serves both the order page and the form's live preview. The same function adds the stock check: on hand at the order's branch, minus what approved, in-progress and completion-pending orders there still need ("committed", scaled by the same `scaleOrder`), against what this run requires — also derived, with no reservation table.
- **Conversions** (Week 7 Task 1): `ConversionOrder` (`ConversionStatus`: created `PENDING_APPROVAL` → `APPROVED | REJECTED`) records a conversion already done — unsold Lechon into Lechon Paksiw — with the source used and output made. Its added ingredients are derived from the pinned conversion BOM scaled by the source used. Accounting's approval moves the stock in one transaction (source lots out soonest expiry first, ingredients out, output lot `CNV-…` in) and records its cost: the source at its lots' recorded cost plus the ingredients at reference prices on the conversion date. `ConversionOrderService.conversionEffect` is the one calculation behind the form's live preview, the order page, the inbox and the approval.
- **Write-offs** (Week 7 Task 2): `WriteOff` (`WriteOffStatus`: created `PENDING_APPROVAL` → `APPROVED | REJECTED`) takes part of one finished-goods lot at one branch out of stock — expired, spoiled, damaged, failed quality, other — at the lot's recorded cost. Recording submits it; accounting's approval writes the `WASTE` movement and records `totalCost`, the peso value lost. Pending write-offs count as claimed for further write-offs of the lot and for conversions.
- **End of day** (Week 7 Task 4): `EndOfDayService.forDay(date, branch, viewer)` reads one Manila business day of finished goods from the ledger — opening, produced, converted in / out, written off, distributed, closing, per good and branch, in quantity and at lot cost — checks opening + flows = closing (and, for today, closing = the stock levels), and lists the documents behind each flow. Shown on `/inventory/end-of-day`; the 21:00 `end-of-day-summary` job sends the same figures. Nothing is stored.
- **Distribution** (Week 8): `StockTransfer` / `StockTransferItem` — a Transfer Order (`TransferStatus`: `PENDING_APPROVAL → APPROVED → RECEIVED`, or `REJECTED`) of finished goods from a commissary to another branch, one line per good. `StockTransferService` derives what the sender can send (unexpired lots less what pending conversions, write-offs and transfers have claimed) and plans lots with the same `planFefoTakes` conversions use. Task 2 records and lists them (`/inventory/transfers`); a branch manager's view is narrowed in the service to the branch they manage (`Branch.managerId`). Accounting's approval (`POST /api/approvals`, `StockTransferRepository.decide`) is the dispatch: lots locked with `lockLots` (lines in good-id order), re-planned with `planFefoTakes`, taken out as `TRANSFER` (−). The receiving branch's manager or an admin confirms receipt (`StockTransferRepository.receive`): what arrived of each lot (counted per lot, Task 4) arrives via `FinishedGoodStockRepository.transferIntoLot` as `TRANSFER` (+); the shortfall has no movement — lost in transit — and its value at lot cost, reason and note are stored on the transfer in the same transaction (logged, not approved; reason labels in `lib/transfer-variance.ts`, shared with the client form). Notifications go through the queue (`transfer-submitted`, `transfer-decided`, `transfer-received` — the last also sends `TRANSFER_VARIANCE` to accounting and admins when it arrived short).
- **Outlet sales** (Week 10 Task 1): `OutletSale` / `OutletSaleItem` — one per outlet per business day, recorded by its manager, no approval. `OutletSaleService` checks stock with the transfers' `availabilityAt`; `OutletSaleRepository.create` locks the lots (`lockLots`, goods in id order), plans with `planFefoTakes` and takes them out as `OUT` movements (`referenceType 'OutletSale'`) in the same transaction as the sale — End of Day's `sold` flow.
- **History data** (Week 10 Task 1): `prisma/history/` (`npm run seed:history`) simulates 90 days day by day and writes them through the repositories' ledger functions (`InventoryRepository`, `FinishedGoodStockRepository`) on per-document transactions, then back-dates the rows. It is not imported by the app.
- **Costing dashboard** (Week 8 Task 6): `CostingService.dashboard(range, viewer)` reads the costs recorded at sign-off — `ProductionOrder.actualCost`, `ConversionOrder.conversionCost` / `sourceCost`, `WriteOff.totalCost`, `StockTransfer.varianceValue` — over Monday–Sunday Manila weeks and totals them with `Prisma.Decimal`; nothing is stored or recomputed. A figure belongs to the week it happened: a run or conversion by its lot's `producedOn`, a write-off by `createdAt`, a shortfall by `receivedAt`; only signed-off records count, and what is still pending in the range is counted for a note. Production cost = batches + conversion ingredients (the source was already a batch); cost per unit of a good is weighted (Σ cost ÷ Σ made).
- **Calendar** (Week 10 Task 5): `Holiday` (one per date, typed by `HolidayType`), kept in Master Data → Holidays through `HolidayService`.
- **Approvals**: `Approval` is polymorphic (`referenceType` + `referenceId`), one row per decision on a PR, PO, RR, production order plan (`ProductionOrder`), production completion (`ProductionCompletion`), conversion (`ConversionOrder`), write-off (`WriteOff`) or transfer (`StockTransfer`). PR, PO and RR carry `submittedAt` for the inbox's waiting time (Week 11 Task 1).
- **Notifications**: `Notification` rows per user, unread while `readAt` is null. **Email** (Week 11 Task 2): each notification whose type is in `EMAILED_TYPES` is also queued as an email to the user's `notificationEmail`; `EmailLog` records what happened to it.
- **AI** (Week 9): `AiCall`, one row per Claude API call — feature (`AiFeature`), outcome (`AiCallOutcome`), tokens, estimated `costUsd`, time, who asked (null for jobs). The monthly budget and AI Settings (`/admin/ai`, `AiService.overview()`) read it. `AiQuery` (Task 4), one row per assistant question — its lookups, answer or error, and its rounds as the `AiCall` rows pointing at it; with Task 5, the document drafted on it (`action*` columns) and what the user decided. `AiInsight` (Task 2), stored AI output about one record — type, polymorphic reference, `PENDING / READY / FAILED`, the text with the facts and prompt it came from, and the `AiCall` that wrote it; one per (type, record).

See [database.md](database.md) for relationships, indexes and migration rules.

## Infrastructure

- **PostgreSQL 16** and **Redis 7** run via `docker-compose.yml` for local development (health-checked, persisted to named volumes).
- **BullMQ**: `lib/queue.ts` is the producer (lazy `Queue` on `globalThis`, so importing it opens no connection — `next build` must not need Redis). `worker/index.ts` is the consumer, run as a **separate process** with `npm run worker` (watch) or `npm run worker:start`. A `Worker` inside the Next.js process would be duplicated on every hot reload, so nothing under `app/` imports `worker/`. The worker is thin and delegates to services (`NotificationService`). Jobs: `pr-submitted` → notification rows for approvers minus the requester; `production-order-submitted` → approvers minus the submitter; `production-order-decided` → the submitter, and on approval with shortages the ordering roles minus the approver; `production-completion-reported` → approvers minus whoever reported the run done; `production-completion-decided` → whoever reported it (the reporter is read from the status log, since a send-back clears `completedById`); `conversion-order-submitted` → approvers minus whoever recorded it; `conversion-order-decided` → whoever recorded it; `write-off-submitted` → approvers minus whoever recorded it; `write-off-decided` → whoever recorded it; and four **scheduled** jobs: `low-stock-check`, `stock-reconciliation` and `expiry-check` (Week 7 Task 3: finished-goods lots expired or expiring within 24 / 48 h → one summary per production manager and admin) daily at 06:00 Manila, and `end-of-day-summary` (Week 7 Task 4: the day's finished-goods figures and closing value → one summary per production manager, accountant and admin; nothing on a day with no movement) daily at 21:00 Manila. Week 11 Task 3 adds the scheduled `approval-escalation` (hourly 07:00–21:00 Manila → `NotificationService.notifyOverdueApprovals`: everything in the approvals inbox waiting ≥ 24 h — the inbox's own list and `pendingSince` — reminded to each approver who did not submit it, once per 24-hour step, claimed in `ApprovalReminder` first; one `APPROVAL_OVERDUE` digest per approver, emailed). Week 11 Task 2 adds `pr-decided`, `po-submitted`, `po-decided`, `rr-submitted`, `rr-decided` (the procurement events that notified nobody before) and a third queue, **`email`** (see "Email is a copy" above). A second queue, **`ai`** (Week 9), has its own `Worker` in the same process with concurrency 2, so slow Claude calls never hold up notifications: `cost-variance-explain` → `CostVarianceService.explain()` (retried per `AI_JOB_OPTIONS`; if a job dies on its last attempt the insight is marked `FAILED`). Scheduled jobs are listed in `DAILY_JOBS` (`lib/queue.ts`) and registered by the worker at startup with `upsertJobScheduler` — keyed by name, so a restart replaces rather than duplicates, and the schedule lives in Redis, so a run missed while the worker was down happens when it is back. Not an OS crontab: nothing runs unless the worker does. `npm run job -- <name>` enqueues a scheduled job immediately. A scheduled job that notifies uses the run's date as `referenceId` to send at most once per person per day.
- **PDF**: `GET /api/purchase-orders/[id]/pdf` renders with `@react-pdf/renderer` in the request (Node runtime). Money prints as `PHP 1,420.00` — the built-in PDF fonts have no `₱`.
- **Environment config** is centralized in `lib/config.ts`, which throws at import if `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET` or `NEXT_PUBLIC_APP_URL` is missing. The worker loads `.env` itself via `tsx --env-file=.env`. Three optional variables (Week 9): `ANTHROPIC_API_KEY` — without it AI features answer "not set up" and nothing else changes — `AI_MONTHLY_BUDGET_USD` (default 20; a malformed value fails at startup), and `AI_DATABASE_URL`, the assistant's read-only `kitchen_ai_reader` login (without it the assistant is not offered `run_query`).
- No cache, file storage, or deploy target yet — see [deployment.md](deployment.md).

## Conventions to follow when extending this

- New features follow route handler → service → repository; never call `prisma` from a route handler, page or service.
- Keep secret-bearing fields out of repository return types — follow `safeUserSelect` / `SafeUser`.
- Route-level access belongs in `middleware.ts` `ROLE_GUARDS`. A service-level role check is for an *action* the path cannot distinguish (see "Authorization: path vs action"), not a substitute for a guard.
- Anything `middleware.ts` imports must stay Edge-safe; `lib/queue.ts`, `lib/realtime.ts`, `lib/claude.ts` and `lib/auth.ts` are Node-only.
